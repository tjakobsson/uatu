## Context

See proposal.md — Why. The relevant plumbing today:

- The session child derives `ChatActivity = { working, awaiting }` in `ChatAdapter.activity()` (`src/chat/adapter.ts`): `working` is `liveTurns.size > 0`, and a conversation enters `liveTurns` only when its status satisfies `isLiveConversationStatus` (`running | sending | retrying | compacting`). The `background` status — Claude Code's "no turn, but live background tasks" — is deliberately excluded because `liveTurns` also gates the composer's Cancel and held-prompt logic (`adapter.ts` ~495, ~1122, ~1530), where a background conversation must accept a prompt.
- The child's `GET /api/activity` SSE emits those two booleans on change. The hub's `LiveBroker` holds one `ActivityFeed` per user; `refreshFeed` attaches one shared per-workspace `activity` upstream per running workspace and folds the hub's `running` fact in, yielding `WorkspaceActivity = { running, working, awaiting }` (`src/shared/live-protocol.ts`, sanitized on both sides). **A user's feed is discarded when their last stream detaches** (`live-broker.ts` ~330), and the upstream is only attached while at least one user's feed exists.
- `src/shell/hub-nav.ts` renders `workspaceMenuState` (`stopped` / `working` / `awaiting you` / nothing for idle) and `switcherBadge` (awaiting count pill outranks the working dot), counting other workspaces only.
- The session page already knows when its chat is "in view": `chatSurfaceActive()` in `src/chat/ui.ts` (document visible, and the chat panel open on desktop / the chat tab active in touch mode), used to clear the page-local `pendingNewContent` badge.
- The hub intercepts a few session-path routes before proxying (`/s/<ws>/api/personal-state` in `src/hub/server.ts`), CSRF-checked.
- Background tasks are one `background_task` item kind updated in place (`src/chat/claude/normalization.ts` `backgroundTaskUpdate`; archived design `2026-09-02-polish-claude-code-chat` D8). Kept today: `task_id`, `description`, `task_type`, `tool_use_id`, progress (`task_progress.summary`, else `Using <last_tool_name>`), settled status and summary. Dropped: `task_started.prompt`/`subagent_type`/`spawn_depth`, `task_progress.usage`, `task_notification.output_file`, and the launching tool result's async `AgentOutput` (`agentId`, `outputFile`, `prompt`). The SDK options `agentProgressSummaries` (model-written progress for agent tasks, ~30 s cadence) and `forwardSubagentText` (forward subagent text, not only tool blocks) are not set. Running tasks are pinned above the composer (`ui.ts` `syncBackgroundTasks`, `runningBackgroundTasks` — no status gate, so they show mid-turn) with a Stop button and nothing else clickable; the timeline hides running task rows.
- Subagents: a child conversation id is `sub:<parentSessionId>:<agentId>`, set on the launching `tool` row's `childConversationId` from the tool result's `agentId` — i.e. only when the run ends (a backgrounded Agent's async result carries `agentId` at launch, but it is not read). The subagents track (`ui.ts` ~1069) renders an "open" button only when `conversationId` exists, else a plain label; so a running subagent cannot be opened. A Claude child's projection is filled from the subagent `.jsonl` on open and refreshed only on snapshot/gap: the provider emits every event under the parent session id, and frames tagged `parent_tool_use_id` are ignored as stream events or normalized into the parent. OpenCode children are live through the same drill-down, so the client side of a live child already exists.
- The SDK: `task_started` carries `task_id`, `tool_use_id`, `description`, `subagent_type`, `is_backgrounded`, `prompt`; `task_progress` carries `usage { total_tokens, tool_uses, duration_ms }`, `last_tool_name`, `summary`; `task_notification` carries `status`, `output_file`, `summary`, `usage`; `tool_progress` carries `task_id` and `subagent_type`. There is no output stream for a shell task — the model reads it through `TaskOutput`; the `BashOutput` result of a backgrounded command carries `backgroundTaskId` but no path.

## Goals / Non-Goals

**Goals:**
- Keep the child's activity contract at two booleans; the hub composes the fourth fact.
- Keep `liveTurns` semantics untouched; background work reaches `working` through a sibling set.
- Marks survive a user closing every page (broker-level, hub-lifetime) and are cleared for one user without touching another's.
- One change to the activity wire shape (`finished`), consumed by the existing topic and client channel — no new topic.
- Inspection reuses the existing child drill-down and live child subscription; a shell task's output is the one new read.
- Everything a running task shows comes from what Claude Code already reports; no scraping of the CLI's UI.

**Non-Goals:**
- Persisting finished/viewed marks across hub restarts.
- Per-conversation granularity in the workspace summary (which conversation finished) — it stays bounded.
- Detecting a finish while no user has any page open (no upstream is attached then; see Risks).
- Dashboard (`src/hub/pages.ts`) or Desktop presentation; push-notification behaviour; OpenCode background work (none exists).
- Streaming a shell task's output character by character; a bounded tail refreshed on a timer while the view is open is enough.
- Restructuring how subagent tool rows appear in the parent timeline beyond what routing to the child requires.

## Decisions

**D1 — Background work reaches `working` through a separate set, not by widening `isLiveConversationStatus`.**
`ChatAdapter` gains a `backgroundWork: Set<conversationId>` maintained in the same projection status callback as `liveTurns` (`status === "background"` adds, anything else deletes; `forgetActivity` clears both). `activity().working = liveTurns.size > 0 || backgroundWork.size > 0`. The e2e fixture `tests/e2e/chat-service.ts` mirrors the rule. *Alternative rejected:* widening `isLiveConversationStatus` — it would make the composer offer Cancel and hold prompts during background work, contradicting `claude-code-chat`'s "prompting SHALL remain possible".

**D2 — `finished` is a per-user fact composed at the broker from two broker-level marks.**
The broker watches every running workspace's activity for the hub's own lifetime, not only while some user's feed exists: the fact is for work that finished while the user was away, and a page-scoped upstream cannot see that (see D11). `LiveBroker` keeps, independent of any `ActivityFeed`:
- `observed: Map<workspaceId, WorkspaceActivity>` — the last sanitized value seen from the workspace's activity upstream (any user's attachment updates it; the upstream is shared).
- `finishedAt: Map<workspaceId, number>` — a monotonic stamp, set when `observed` goes from `working: true` to `working: false && awaiting: false` while running; deleted when the hub observes the workspace stop, when it becomes `working` again, or when it leaves the registry (the registry's forget path tells the broker, since a freed slug can be reused by a new workspace). An upstream reporting `unavailable` does NOT delete it: that fires on the first failure of any episode, including a single stream end the retry recovers from, and erasing an unviewed finish on a transient drop is the loss the persistence exists to prevent. `unavailable` instead records the workspace as unreachable (`observed` set to not running), so a feed refresh cannot resurrect it as running and the recovered upstream's first frame has no working predecessor to misread as a finish.
- `viewedAt: Map<user, Map<workspaceId, number>>` — set by `acknowledgeViewed(user, workspaceId)`.
A user's feed value is `{ running, working, awaiting, finished: running && !working && !awaiting && finishedAt > (viewedAt ?? -∞) }`. `setFeedValue` compares all four (`sameActivity`). `acknowledgeViewed` re-derives and re-emits for that user's feed only. *Alternative rejected:* keeping marks in `ActivityFeed` — lost when the user's last page closes, which is exactly the "switched away and came back later" case the issue describes. *Alternative rejected:* deriving from the push `turn-completed` stream — it is suppressed for the background phase and would need a second observer; the activity transition is agent-agnostic and already flows through the broker.

**D3 — Transitions are detected only from observed values.** `RUNNING_UNKNOWN → facts` never counts (no prior `working: true`), so a page opening onto an already-idle workspace does not invent a finished mark. `working → awaiting` is not a finish; `awaiting → idle` without an intervening `working` is not a finish either (the answer was given from somewhere the user was looking).

**D4 — Acknowledgement is an explicit, hub-only POST from the viewing page.**
`POST /s/<ws>/api/activity-viewed` (hub-handled beside `/api/personal-state`, CSRF-checked, 204, 404 for an unknown workspace). The client calls it from `hub-nav.ts`, which already holds the activity map and knows hub mode, whenever both hold: the current workspace's feed value reads `finished` and the chat surface is active. Triggers: an activity update for the current workspace, and a `uatu:chat-surface-active` document event that `src/chat/ui.ts` dispatches at the point where it clears `pendingNewContent` (surface just became active) and once at bootstrap if already active. Pages without a hub never post. *Alternative rejected:* clearing on stream presence for that workspace — a hidden background tab would clear a finish the user never saw. *Alternative rejected:* posting on every activation unconditionally — harmless but noisy; the conditional form also removes the ordering race where an ack lands before the mark exists.
The momentary `finished: true → false` round trip on the viewing user's other pages when the finish happens while they are looking at that workspace is accepted (a single re-emit, no user-visible flicker at the badge's transition speed).

**D5 — Switcher presentation.** `WorkspaceMenuState.tone` gains `"finished"`, text `finished`; the row states are mutually exclusive by construction, since `finished` requires `!working && !awaiting`. `SwitcherBadge` gains `{ kind: "finished", count }`; `switcherBadge` returns awaiting if any, else finished if any, else working; label `Work finished in N workspace(s)`. CSS: `.hub-menu-state.is-finished` and `.hub-activity-badge.is-finished` use their own pink `--finished` tone (GitHub's pink pair) as a count pill without the awaiting pulse/warm colour, so finished reads apart from blue working and amber awaiting at a glance and the three badges read as three levels.

**D6 — A running task carries its facts on the existing item; the SDK is asked for progress summaries.**
`BackgroundTaskItem` gains optional `subagentType`, `prompt`, `usage: { totalTokens, toolUses, durationMs }`, `outputFile`, and `childConversationId`; `backgroundTaskUpdate` keeps them from `task_started` / `task_progress` / `task_notification`, and the launching tool result's async `AgentOutput` supplies `agentId` (→ `childConversationId`) and `outputFile` at launch. The query is started with `agentProgressSummaries: true`, so an agent task's `progress` becomes Claude Code's model-written one-liner (falling back to `Using <tool>` as today). Elapsed time is derived on the client from `createdAt`; for a shell task it is the only live signal (the spike found `local_bash` emits no `task_progress` at all), so a shell row's progress line is the elapsed readout, never `Using <tool>`. A shell task's `outputFile` is known at launch: the launching Bash tool result's text names it (`Output is being written to: <path>.`), and the convention `<tmpRoot>/claude-<uid>/<cwdSlug>/<sessionId>/tasks/<task_id>.output` is the fallback; `task_notification.output_file` then only confirms it. *Alternative rejected:* a separate "task detail" fetch — the facts are small, already stream in place (D8 of the archived polish change), and the composer row re-paints on change.

**D7 — Inspection is a drill-down: the child transcript for agents, a task view for shell tasks.**
Composer task rows and subagents-track rows become buttons while running. An agent task opens `openChildConversation(childConversationId)` — the same drill-down subagents use after they finish — with a header strip (progress note, elapsed, tokens/tool uses, Stop) drawn from the task item and kept in sync by the existing repaint. A shell task opens a task view in the same drill-down chrome: description/command, elapsed, latest progress, Stop, and an output pane fed by a new child route `GET /api/chat/conversations/:id/tasks/:taskId/output` that returns a bounded tail of the task's `outputFile` (capability-gated; the client names only the task id, never a path; the child reads solely the path the provider recorded from a CLI frame or tool result for a task owned by that conversation, and refuses it unless its real path ends in `/tasks/<taskId>.output` — the CLI's task-output root lives under the OS temp directory, not `~/.claude`, so a config-directory guard would refuse every shell task; 404 until the path is known). The client re-fetches on a short timer while the view is open and the task is running, and once more on settle. *Alternative rejected:* tailing through the live stream as conversation events — it would put shell output on the conversation topic (and into every subscriber's projection) for a view only one page has open. *Alternative rejected:* a modal — the drill-down already handles the child/parent navigation and touch layout.

**D8 — Subagent frames are routed to the child conversation so an open transcript is live.**
The provider learns an agent task's child id at start: for `local_agent` tasks `task_started.task_id` *is* the subagent's agent id (the `agent-<id>.jsonl` name and the tool result's `agentId`), for foreground and backgrounded runs alike — confirmed by the spike and keeps a `parentToolUseId → childConversationId` map for the session. Frames tagged `parent_tool_use_id` are then normalized and emitted under the child's id (with `forwardSubagentText: true` so text and thinking arrive, not only tool blocks); the adapter's existing child routing (`normalized.conversationId` with `parentId`) publishes them on the child's `conversation` topic, which the drill-down already subscribes to. The launching row's attribution (model, usage) keeps coming from the tool result as today. Frames for a child whose id is not yet known keep today's behaviour. *Alternative rejected:* watching the subagent `.jsonl` and re-snapshotting the open child — simpler in the provider but polling, duplicates the transcript reader on every change, and does not help the subagents track name progress. *Risk acknowledged:* the parent timeline today may carry subagent tool rows from those frames; routing to the child changes where they land, which the spec already prefers ("rendered from the run's own activity"). The implementer verifies with `timeline-renderer.test.ts` "subagent entries" what the parent must keep (the launching row only).

**D9 — Spike before the inspect work.** A timeboxed session against real Claude Code (a backgrounded Bash, a backgrounded Agent, a foreground Agent, `/code-review`) records the SDK frames and tool results to confirm: the task-id ↔ agent-id relation for `local_agent`; where a *running* `local_bash` task's output lives and whether any frame names it before `task_notification`; how `/code-review` reports its tasks and agents (backgrounded or foreground). Findings are written to `openspec/changes/fix-workspace-activity-states/spike-background-tasks.md`. Outcome (`spike-background-tasks.md`): all three questions answered live against the SDK-bundled CLI 2.1.261. The task id is the agent id (D8 stands); the shell output path is known at launch (D6/D7 adjusted above); `/code-review` at its default levels runs as a *Skill fork* — frames under the Skill tool use's `parent_tool_use_id`, no task frames, no background work — so it gains nothing from this change beyond the normal working state, and a live drill-down for skill forks (whose agent id is only known when the fork ends) is a follow-up, not in scope. Two lifecycle facts the implementer must respect: a single-string prompt would make the SDK reap background tasks at the first result (Uatu's streaming prompt queue already avoids this), and the CLI's own follow-up turn after a notification opens with a fresh `system/init` carrying the same session id.

## Risks / Trade-offs

- [A hub-lifetime activity upstream per running workspace costs one child subscription each, held whether or not anyone is watching] → Bounded by the number of *running* workspaces (the hub already holds a child process for each), released the moment a session stops, and it is the only way the fact can cover the case it exists for (D11).
- [Persisted marks are one more file the hub must keep coherent] → Reuses the personal-state store's shape and failure behaviour: a write failure degrades to memory-only, and an unreadable file starts empty rather than refusing to serve (D12).
- [Workspace-level granularity: viewing the chat with a different conversation open still counts as viewed] → Accepted; the summary is bounded by spec and the badge's job is to prompt a look, not to track reading.
- [Every consumer that asserts exactly three activity keys breaks] → Tests updated in the same change; the sanitizer tolerates a missing `finished` (treated false) so an older child/hub pairing degrades to today's behaviour.
- [Three badge kinds on one chip add visual vocabulary] → Awaiting keeps its warm amber pill, finished is a pink pill, working stays the small pulsing blue dot; e2e screenshots capture all three.
- [`agentProgressSummaries` forks the model every ~30 s per running agent task — extra tokens and cost] → Summaries are attributed nowhere today; accept the cost as the price of a readable progress line, and note it in the PR. If it proves noisy, the option becomes a per-workspace setting later.
- [`forwardSubagentText` raises the frame volume of a chatty subagent] → Frames are routed to the child only; the parent's projection is untouched; the child's topic is subscribed only while a drill-down is open (hub-live-stream "Closing a subagent transcript stops its events").
- [The shell-output route reads a file path reported by the CLI] → The client names only a task id; the child reads solely the path the provider recorded from a CLI frame or the CLI's own launch sentence for a task owned by that conversation, refuses it unless its real path ends in `/tasks/<taskId>.output` (the CLI's task-output root is under the OS temp directory, so a config-directory guard would refuse every shell task), and returns a bounded tail aligned to a character boundary (no whole-file reads). The launch sentence is matched as the CLI writes it, so a command's own output cannot supply the path.
- [Routing subagent frames to the child could remove rows the parent timeline shows today] → Covered by the renderer's existing subagent tests; the launching row stays, and the spec prefers the child as the run's home.

**D10 — A forked skill is adopted by its launching tool use, not by an id it does not yet have.**
The spike found that Claude Code runs a skill like `/code-review` as a *fork*: frames stream under the Skill tool use's `parent_tool_use_id` from the first moment, but the fork's `agentId` appears only in the tool result, when the run ends — the opposite of an agent task, whose id is known at its start edge (D8). So the provider buffers frames for an unknown `parent_tool_use_id` against that tool use, bounded in count and dropped when the session retires; when a tool result carries `status: "forked"` with an `agentId`, the child is opened as `sub:<sessionId>:<agentId>`, the buffer is replayed into it in arrival order, and later frames route straight through. The launching row gains its `childConversationId` at the same moment. Until the result lands there is no id to click, so the row offers no transcript and the fork's tool activity in the parent timeline is what shows the run is alive; the buffer's whole purpose is that the transcript is COMPLETE the moment it does open, rather than starting at the end. The spec was corrected to promise completeness rather than a live fork transcript, because the two cannot both hold under this decision. *Alternative rejected:* minting a provisional child id keyed on the tool use and renaming it later — the id is the conversation's identity on the wire and in the client's open drill-down; renaming it mid-run would break the subscription the drill-down holds.

**D11 — The activity upstream per running workspace is the hub's, not a feed's.**
`refreshFeed` attaches an upstream per *user feed*, so with no page open there is no upstream and no observation. The broker instead holds one activity attachment per running workspace, opened when the session starts and released when it stops, feeding `observeActivity` exactly as a feed's sink does today; a user's feed then only *reads* the composed value. This keeps one upstream per workspace rather than one per user (it already deduplicates), and makes the marks independent of who is looking. The production hub arms watching when the broker is constructed, so every running workspace is watched from the moment the hub starts, whether or not any page ever connects — an API client that starts a session and drives its chat through the proxy without opening a page still has its finishes recorded. Brokers built for tests keep a lazy default, armed by their first activity subscription, so the e2e harness and unit fixtures for other topics open no stray child streams. *Alternative rejected:* polling each child's `/api/activity` on a timer — the SSE upstream already exists and a poll would both lag the finish and cost more.

**D12 — Marks are persisted beside the hub's other per-user state.**
`finishedAt` per workspace and `viewedAt` per user and workspace go to a small JSON file in the hub state dir, written debounced on change and read at startup, modelled on `personal-state.ts` (same atomic-write and tolerate-missing behaviour). Only these two maps are persisted: `observed` is a live reading and must start empty after a restart, so the first frame after startup has no predecessor and cannot be read as a transition. Marks for a workspace that left the registry are dropped at load. Only a stop the hub actually observes clears a mark; a workspace that is merely not running when the marks are read back keeps them, since a restart leaves every session stopped and dropping them then would be the amnesia the persistence exists to prevent. *Alternative rejected:* persisting nothing and accepting the restart amnesia — a hub upgrade is exactly when a long agent run is likely to be in flight, and losing the badge then is the case users would notice.

**D13 — An agent run is a run whatever the ambient flag says.**
Q4/Q5 of the spike established, against the CLI Uatu actually runs (the `claude` on PATH, 2.1.280, not the SDK's bundled 2.1.261), that Claude Code marks two kinds of agent run `ambient: true, skip_transcript: true`: a skill the model forks (`task_started` at launch with `tool_use_id` = the Skill tool use and `task_id` = the agent id; its frames stream tagged with that tool use) and the run a typed command launches (`task_started` with NO `tool_use_id`; nothing of the run streams; the review arrives as a `<synthetic>` assistant frame carrying `local_command_source`, then a `result` with `local_command`). A census of 141 recorded runs found every run without a launching tool use was one of these, and no housekeeping run in `subagents/`. So an ambient `task_type: "local_agent"` task is treated as a run: the child `sub:<sessionId>:<task_id>` is opened at `task_started`, the launching row (when there is one) gains its `childConversationId` then, and frames tagged with its tool use route to it as D8 already does. The ambient mark keeps its one legitimate meaning — the run is not background work — so it still never enters `background_tasks_changed`-driven state or the composer's background list. A run with no launching tool use is keyed by its task id in the provider's run map, and the provider emits a run row for it (a `background_task` item carrying `childConversationId` and a `foreground: true` flag) so the subagents track can list it, while the composer's background list and the timeline's settled-task rendering skip foreground rows — the command's own output is the timeline's record of it. *Alternative rejected:* recognising a typed command's run by matching the task's description against the command the user just sent — narrower, and unnecessary once the census showed ambient agent runs are never noise. *Alternative rejected:* a synthetic `Skill` tool row for a typed command — it would show the model making a call it never made.

**D14 — A silent run is followed from its transcript on disk.**
Every forked run's transcript is written live to `subagents/agent-<id>.jsonl` (the census found it appears within ~1.5 s and grows as the run works), and the drill-down already reads a `sub:` child from that file. So while a drill-down is open on a run that is still running and has received no live event for about two seconds, the client re-reads its snapshot on a short interval, stopping when the run settles or the drill-down closes. One rule covers the typed command (which never streams) and is a harmless fallback for any run whose stream stalls; a run that streams keeps updating from its events and never trips it. *Alternative rejected:* tailing the file in the provider and emitting its records as events — more machinery for a view only an open drill-down needs, with no gain over re-reading a snapshot that already dedupes by item id.

With D13, D10's buffer matters only for a CLI that names a fork at its end (as 2.1.261 did); on 2.1.280 a fork is named at its start and followed live. It is kept for that case.

**D15 — A typed command's output is a command output, in the live stream and on reopen.**
The live `<synthetic>` assistant frame that carries `local_command_source` is the command's output, not a model turn: it renders as today, but it does not set the conversation's model or contribute a usage figure. On reopen, the stored `system` record with `subtype: "local_command"` renders the same output, which today is dropped.
