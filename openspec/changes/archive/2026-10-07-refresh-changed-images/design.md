## Context

The preview loads images through the static-file fallback at stable URLs. Within a page, the browser's image cache keys on the URL and reuses a decoded image regardless of `cache-control`, so changing the response headers cannot fix staleness; the URL has to change when the file does. The client's document index holds every watched file's change revision, which the server bumps on every create or modification, binaries included, and `documentRevisionKey` (epoch and revision) already versions the selected image's URL.

## Goals / Non-Goals

**Goals:** a changed image shows its new content in the preview, opened or embedded, without a page reload, a document re-render, or a scroll jump; Follow follows changed images the preview can show, but stays on a document whose own embedded image changed, in whatever view the document is shown; an image Follow switched to behaves as a destination afterwards (reload, resume, Back).

**Non-Goals:** `srcset`, `<picture>` sources, CSS backgrounds, images inside inline SVG, and AsciiDoc interactive SVGs rendered as `<object>` are not versioned. A file-pinned session (scope `file`) only holds the pinned document, so images embedded in it are not versioned. HTTP validators (ETag, Last-Modified) on the static fallback are left as they are; the revision parameter makes them unnecessary for correctness.

## Decisions

- **One versioning mechanism: the change revision.** Every watched image in the preview, opened or embedded, carries `revision=<documentRevisionKey(id)>`, the parameter the selected image already used. Freshness therefore never depends on modification-time equality. The client pass (`refreshImageRevisions`) runs on mount and on every applied patch, frame, or reconcile, and only writes `src` when the URL differs, so it is idempotent and refetches nothing that did not change. Server-side rewriting would still need this client pass for the case where only the image changed (the document is not re-rendered), so the client pass is the one place.
- **Resolve like the server does.** The image's URL is resolved against the per-document base, the session's base path is stripped, the path is percent-decoded, and the first root holding that relative path wins — the static fallback's own order. Anything that does not resolve to a watched file is left alone.
- **Swap `src` on the existing element.** The pass changes the source of the `<img>` already on screen, embedded or opened, so the previous bitmap stays up until the new one has loaded and layout does not collapse. Re-rendering an opened image whose file changed keeps the element and moves its source to the new revision rather than rebuilding it.
- **One predicate for "followable".** `isFollowableFile` (non-binary, or a viewable image name) is shared by the file index's `changedId` nomination, the snapshot's latest change, the client's selection rule, and boot and popstate, so they cannot disagree. The extension list moved to `src/shared/` for that.
- **The embedded-image exception reads the rendered payload, not the DOM.** Source and Diff render no `<img>`, so reading the preview would make the exception work in Rendered view only, and would tie it to reading the DOM before an update lands. Instead `embedded-images.ts` keeps, for the shown document, the authored `src` values of its rendered payload and the document's base URL, filled whenever a rendered payload is fetched (Rendered view, split layout). A Markdown or AsciiDoc document shown only as Source or Diff has its rendered payload looked up once per document revision in the background, just for this, shared by every caller while in flight and bounded to 10 seconds. At event time the sources are resolved against the current roots (so an image created after rendering still counts). Nothing switches, so the URL, history, and the "updated" signal are untouched.
- **Unknown is not empty.** Membership is tri-state in effect: known for the shown document's current revision (a set, possibly empty), or unknown — nothing recorded yet, or recorded for an older revision, since an edit can add or remove images. A document that cannot embed images (text, an image, none) is known to embed nothing. One pure classifier, `imageChangeOutcome` in `follow-rules.ts`, turns a changed image and the membership into `select`, `stay`, or `defer`; `stay` and `defer` hand the selection rule (`nextSelectedDocumentId`, which stays pure and unaware of images) no changed id, so the selection stays put.
- **A deferred decision waits for the lookup and is guarded.** `shell/image-follow.ts` holds one image decision (the latest changed image's) and makes sure the lookup for the current revision is in flight. When it answers: embedded → stay; not embedded → follow; failed (network error, non-OK status, unparsable body, or no answer within the bound) → follow, Rule C's default, since a failed lookup proves nothing about the document and following shows the change instead of losing it. The decision is carried out only if Follow is still on, the preview is not a commit, and a guard key captured when it was deferred still matches: selection generation and user activation (a click, or any other selection change), the Follow-switch count (off, or off and on), and the document's revision. Any other file change applied meanwhile cancels it, so a document change is followed at once. A lookup started for an older decision cannot settle a newer one.
- **One helper for all three paths.** `followableChange` in `events.ts` applies the classifier and the deferral identically on the incremental patch, full frame, and reconcile paths, so they cannot drift.
- **Rule B and the default document stay documents-only.** Their pick is "newest mtime", and image mtimes mostly reflect a checkout or a build, not an edit the user wants to see. Following an image only when it changes keeps Follow predictable.
- **Reload and Back.** The server already answers an HTML navigation to any known file with the SPA shell (an SVG must never run at the app's origin), so only the client had to accept a previewable image for a direct link, the saved document, and popstate.

## Risks / Trade-offs

- A Markdown or AsciiDoc document shown as Source or Diff costs one extra rendered fetch per revision. Until it answers, an image change waits; at worst, when the lookup goes unanswered, for its 10-second bound, after which the image is followed.
- The server nominates one changed file per batch. If one batch changes a document and then an image the shown document embeds, the image is the nomination, the client keeps the current document, and the other document is not followed.
- An embedded image is fetched once without the parameter when a document mounts, before the pass runs, because the HTML is assigned first. Local and cheap; avoiding it would mean rewriting the HTML before assignment.
