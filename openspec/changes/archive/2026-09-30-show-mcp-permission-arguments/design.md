## Context

See proposal.md, Why. The facts the approach rests on, read from the pinned OpenCode sources (1.18.32 `session/tools.ts`, 2.0.18 `tool/mcp.ts` and `permission.ts`) and the real 2.0.13 capture in `tests/fixtures/opencode-v2/real-2.0.13.json`:

- An MCP tool's permission is asked with the tool's registry name as the action (`<server>_<tool>`, both parts sanitized to `[A-Za-z0-9_-]`), `["*"]` as its resources and as its save pattern, and empty metadata. On 2.x it also carries `source: { type: "tool", messageID, id }`, where `id` is the tool call id. On 1.x the server records `tool: { messageID, callID }` on the request; whether the bridged `permission.v2.asked` event carries it is not known from the SDK types.
- The tool call precedes the ask. On 2.x, `session.tool.called` (with input) lands before `permission.asked`, and our tool row's id is `tool:<call id>`, the same id the permission's `source.id` names. On 1.x the running tool part, with `state.input`, is announced before execution asks.
- `pendingPermissionFields` in `src/chat/opencode/normalization.ts` is the one reader for a pending permission's fields, used by the live event on both generations and by both generations' `listPermissions()`.
- `PermissionItem` is a closed wire schema (`additionalProperties: false`); the client parses it in `parsePermissionRequest()`. Under `api/CONVENTIONS.md` a new property on a closed object is a workspace API revision.
- The timeline renderer rebuilds each card from item state and already walks `projection.items` before rendering (active-request selection, subagent labels), so a per-card lookup of another item costs nothing new.
- `permission.replied` arrives as a sparse upsert (`action: "permission"`, no resources); the adapter's permission merge keeps the ask's `resources` and `alwaysPatterns` across it.
- Claude Code's `permissionResources()` already puts an MCP tool's compact JSON input on the card as its resource, so that agent is not affected.

What the captures for this change showed (`.local/mcp-capture/`, the 2.0.18 turn saved as `tests/fixtures/opencode-v2/real-2.0.18.json`):

- OpenCode 2.0.18 asks for an MCP tool exactly as read above (`action: "tracker_create_issue"`, `resources: ["*"]`, `save: ["*"]`, `metadata: {}`, `source: { type: "tool", messageID, id }`), and `source.id` is the id of the preceding `session.tool.called`. That row is the code-mode `execute` call (2.x reaches MCP tools through code mode; the `codemode: false` server option did not change that), so its `name` is `execute`, not the action, and its input is the code holding the arguments. The exact join is the only join there; the name fallback cannot reach it.
- OpenCode's default ruleset allows MCP tools outright: a permission rule (`permission: { tracker_create_issue: "ask" }` on 1.x, `permissions: [{ action, resource: "*", effect: "ask" }]` on 2.x) is what makes it ask. The issue's reporter has such a rule.
- The first run of the built binary against 2.0.18 showed today's card despite the reference: the client's copy of the `execute` row had no `input`. The adapter's event coalescer replaced a buffered upsert with the next one for the same id, and 2.x emits `session.tool.progress` (no input) within milliseconds of `session.tool.called` (with input), so the projection only ever met the sparse frame. The history route reads OpenCode's stored messages, which is why the server's copy looked complete. This is a pre-existing loss of 2.x tool input, not something the new field caused; D8 below is the fix.
- The 1.x classic `permission.asked` carries `tool: { messageID, callID }`, captured live from 1.18.29 for a bash call and already a fixture in `v1/normalization.test.ts`; the bridged `permission.v2.asked` does not. On 1.18.32, four isolated runs (two models) never handed the model the MCP tool although the server reported it connected, so no fresh 1.x MCP capture exists; the 1.x branch of D1 rests on the 1.18.29 event.

## Goals / Non-Goals

**Goals:**
- A wildcard-only OpenCode permission shows the arguments of the call it belongs to, live and after recovery, while it is open.
- The join between permission and tool row is exact where the wire allows it (2.x), and truthful where it does not.
- No new agent-specific knowledge on the client beyond "a wildcard resource says nothing".

**Non-Goals:**
- Rendering the arguments as a schema-aware form. They are shown as the tool row shows them.
- Changing Claude Code's permission cards, or unifying the two agents' resource derivation. Noted as a possible follow-up.
- Changing what "Allow always" installs or how its confirmation reads; a `*` save pattern already produces the "every request under this permission" wording.

## Decisions

**D1. One additive wire field: `PermissionItem.sourceToolId?: string`, the timeline id of the tool row the permission belongs to (`tool:<call id>`).** Filled by `pendingPermissionFields` from 2.x `source.id` when `source.type === "tool"`, and from a 1.x `tool.callID` if the event carries one (settled by the live check in tasks 1.x). Because the live event and the pending list share that reader, the field cannot land on one path and not the other. Carried on `PendingPermission` and mapped in the adapter's seeding, as `alwaysPatterns` is. The permission merge keeps it across the reply's sparse upsert. *Alternative:* resolve the tool row on the server and copy its input onto the permission as a `resources` entry, the way Claude Code's path does. Rejected: the server's normalizer is per event and does not hold the tool row; the client's projection does. Copying would also freeze the arguments at ask time while the tool row is the live record. *Alternative:* no wire field, name-match only. Rejected: 2.x names the call exactly; throwing that away to rely on a heuristic is a worse join for no saving. The heuristic stays as the fallback (D2). A new property on a closed schema is workspace API revision 22 with its own changelog section and migration guidance.

**D2. The renderer resolves the tool row from the projection: by `sourceToolId` when set, else the newest tool row whose `name` equals the request's `action` and that is not yet completed.** The lookup is built once per render from `projection.items` (a map by id, plus the last running row per name) and handed to `renderItem` the way `origin` and `todo` are, so a cached node is invalidated when the linked row's input changes. The name fallback covers 1.x if its event carries no call reference, and any 2.x event that arrives without `source`. When neither finds a row, the card renders as today (D4). *Alternative:* resolve the row inside `renderPermission` by scanning items. Rejected: the renderer's cache key must include everything outside the item that changes its markup, and a scan hidden inside the render function would not feed that key.

**D3. The arguments block is shown only for a wildcard-only request: `resources` empty or every entry `*`, no `diff`, no `plan`.** A bash permission carries its command as a resource and its tool row carries the same command; showing both would duplicate. An edit permission has its diff. The block renders the linked row's `input` as the tool row's default body does (a `<pre>` of the input string), under a lead line naming it as what the call will be given, in place of the wildcard bullet; the wildcard is not drawn beside it. A request that names specific resources never gets the block, even if a tool row is found.

**D4. When no tool row is found, the card is exactly today's card.** The `*` bullet stays; nothing is guessed. The condition is real: a card recovered on load renders before the conversation's history page has been merged, and a 1.x tool part may arrive after the ask under load. Since the lookup is part of the render key, the block appears once the row lands.

**D5. A resolved card recedes as every permission does: the arguments block falls away with the choices, the diff's rule.** The arguments are a preview of what "Allow" would run, and once answered the call is on the tool row directly beneath, input and output together; repeating them on the receded card would make a resolved MCP card taller than a resolved bash card for a fact the transcript already shows once. The resources list (the `*`) stays, so the receded card still says what OpenCode sent. *Alternative:* keep the block, reading the arguments as "what the request named". Rejected for the duplication above; the tool row is the record of what ran.

**D6. The summary names the server and the tool: `Permission: MCP github › create_issue`.** The action OpenCode sends is `<sanitized server>_<sanitized tool>` on both generations (`namespace(server) + "_" + tool`, each half with anything outside `[A-Za-z0-9_-]` replaced by `_`), and both generations report the connected servers (`mcp.status` on 1.x, `mcp.list` on 2.x). Matching the action against `<sanitized server>_` for each reported server, longest first, with a non-empty remainder, is exact: the provider resolves it and puts `mcp: { server, tool }` on the request (D9). The card reads the server as the user registered it and the tool as it resolved; a request that resolves to no server shows the action as sent. The Allow-always confirmation keeps the raw action, because that string is the rule OpenCode installs. *Alternative:* keep `Permission: <action>` (the first cut). Rejected by review: a user reading `tracker_create_issue` cannot tell it is an MCP call, nor which server, and that is half of what the issue asks for. *Alternative:* split the name on the client. Rejected: the client has no server list, and splitting by underscore alone is a guess.

**D8. The coalescer folds a later upsert into the buffered one with the projection's own merge (`mergeInteraction`), passed in as an option.** The window then produces what applying the two frames one after another would have, so a sparse `session.tool.progress` cannot strip the input `session.tool.called` carried. The coalescer keeps no adapter import (the adapter imports it; a cycle would be the TDZ hazard `CLAUDE.md` warns about); the merge arrives as `CoalescerOptions.mergeUpsert`, and without one the coalescer replaces as before. *Alternative:* teach the coalescer tool-specific field rules. Rejected: a second copy of the merge rules that would drift from the projection's. Found by task 5.3; the arguments block cannot work on 2.x without it, and 2.x tool rows had been losing their input on this timing all along.

**D9. One more additive wire field, `PermissionItem.mcp?: { server, tool }`, resolved by the provider.** Each generation's provider keeps the set of reported MCP server names, fetched on first need and dropped on any `mcp.*` event so a server added mid-session is seen; a permission whose action resolves to none refetches once before giving up. The same resolution runs on the live announcement and on the pending list, so a recovered card names the server as a live one would. Normalization stays stateless: it has no server list, so the provider annotates the normalized upsert after the fact. Same unreleased revision 22 as `sourceToolId`.

**D7. Verification against real servers, both generations.** A stdio MCP server with one tool that takes arguments (a few lines on `@modelcontextprotocol/sdk`, already a transitive dependency, or a shell-script server) is registered in a throwaway workspace's `opencode.json`, and the dev hub drives a prompt that calls it. The 1.x capture settles D1's 1.x branch; both captures become normalization fixtures and the before/after screenshots. This is also how the e2e fake's seeded shape is kept honest.

## Risks / Trade-offs

- [The 1.x event carries no call reference and the name fallback picks the wrong row when the same tool is called twice in one step] → OpenCode asks permission at execution, and parallel calls of the same MCP tool in one step are rare; the fallback prefers the newest row not yet completed, which is the one asking. The exact join on 2.x is unaffected. If the 1.x capture shows a call reference, the fallback is rarely reached at all.
- [The tool row's input has not arrived when the card first renders (recovery before history merge)] → D4: the card renders as today, and the render key includes the lookup, so it fills in when the row lands. No spinner, no placeholder text.
- [Strict API consumers reject the new field] → workspace revision 22 with a Migration section; `api/contract.test.ts`, route coverage, and the compatibility step run in CI; run `bun run test:api` locally before opening the PR.
- [An MCP input is large] → it is the same string the tool row already renders in full; the card gets the same `<pre>` and inherits the same bounds. If a tool row later gains a folded input, the card should share it.
- [`resources: ["*"]` from a non-MCP source (a custom tool, a plugin) gets an arguments block it did not ask for] → that is the right outcome: a wildcard says nothing, and the row named `action` is the call being asked about.

## Migration Plan

Ships in one PR. Older clients see a card without the block; the field is optional and absent on items produced before the change. No data migration. Rollback is a revert.
