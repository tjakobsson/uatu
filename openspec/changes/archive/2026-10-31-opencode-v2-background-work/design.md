## Goals / Non-Goals

**Goals:** Put V2-specific evidence/correlation behind the existing provider seam; use one canonical worker state across task lists, launcher presentation, child views, and workspace activity; keep read-side recovery distinct from execution mutations.

**Non-Goals:** No generic public job API, scheduler, new provider, independent worker store, model delegation policy, direct child composer, or automated changes to user instructions. No new push category. No assertion of service-restart survival. Foreground tools and Claude/V1 retain their own lifecycle rules.

An approved optional documentation tip may recommend background subagents for independent work when useful non-overlapping work can continue. Dependent work stays foreground; avoid overlapping writes or use isolation, and rely on provider notifications rather than polling. This exception permits user-facing advice only: do not install/edit project instructions, agent configuration, or defaults, and do not prescribe background execution unconditionally.

## Decisions

### D1. Separate launcher state from worker state

Retain the original `ToolItem` and its successful launch outcome for usage attribution and inspection; add the correlated `BackgroundTaskItem` through the existing normalized upsert seam. Native `running/completed/error/cancelled` maps to `running/completed/failed/stopped`. `toolUseId` links the task to its launching call, `childConversationId` remains the native child session ID, and `subagentType` is the chosen agent rather than an invented worker mode.

Present one logical worker entry, not one entry per evidence frame. This does not remove the existing subagent track's one-row-per-task contract: keep distinct launching task rows and distinct-child/task summary counts, while the live worker count deduplicates calls sharing one execution. Extend renderer correlation to terminal tasks as well as running tasks: worker outcome wins for the subagent card/track, while tool execution itself remains successful. The launcher says “Started in background” until there is a report; its result section links to the canonical settled task result rather than displaying the provider's launch instructions or duplicating the report. Keep existing model/cost attribution on launcher rows; task usage only carries quantities actually reported, never guessed progress/tokens.

Alternative rejected: rewriting the launcher's tool status to running. It conflicts with monotonic tool merges, corrupts the provider's completed call, and recreates the defect on history replay.

### D2. A V2-local worker projection, not a second generic task framework

Add a focused module under `src/chat/opencode/v2/` to fold raw tool facts, synthetic notices, execution evidence, and complete stored history into normalized worker items. Live and stored paths use the same reducer/correlation rules. Its scope keys include workspace/provider, parent, child or shell identity, and an occurrence anchor; memory is bounded and reconstructable. A stored parent history fold is performed before slicing pages, so a launch and its completion on different pages still agree. Active tasks and their launcher references ride the first snapshot just as out-of-page launchers do today.

Do not use child ID alone as a lifetime task ID: a child can run again. Use the first associated launcher call as the ordinary occurrence anchor; a subsequent continuation after a terminal occurrence gets a new anchor. Multiple launchers demonstrably joining the same live child share one worker occurrence/count and retain their individual tool rows. A notification-first occurrence can be anchored by its notification ID, then reconciled with the launch when found, retiring any provisional duplicate in the same update batch.

Metadata establishes authorship/identity/state; envelope text supplies the report body only after that metadata is validated. Deduplicate pending-inbox, delivered synthetic, stored history, and replay by synthetic message/inbox ID. Text that merely resembles `<subagent>` in a human message is inert text, not a state transition. Validate parent-child ownership before accepting a child correlation or control.

The native metadata omits a job generation/call ID. Match repeated-child notifications only when ordered authoritative parent history plus child prompt/execution evidence identifies an occurrence unambiguously; never assign by description text or “latest child” alone. An ambiguous notification remains a readable, child-linked result with its own stable ID while affected occurrence state is marked uncertain pending reconciliation. It must not settle a newer run speculatively. This limitation is explicit rather than inventing a provider field.

Alternative rejected: XML/regex-only detection or `taskId = childID`; either misattributes human content or later continuations.

### D3. Recovery returns evidence, not absence-as-cancellation

Reuse `listBackgroundTasks` where it is authoritative (Claude), but add an optional **scoped** provider reconciliation operation, `reconcileBackgroundTasks(sessionId)`, for V2. It returns normalized worker items (running and terminal, with stable IDs), including explicit uncertainty, for the requested verified parent. This avoids scanning every workspace's entire history on every snapshot and avoids abusing a live-only list to encode terminal facts. Do not implement V2 by returning an incomplete empty list to the adapter's existing “missing means stopped” rule.

Read-side algorithm:
1. Subscribe to the provider stream and establish its connected marker; buffer or generation-guard worker updates during reconciliation so there is no subscribe-after-read gap.
2. Read the parent's complete stored history plus **all** pending inbox items (separate from steering's user-only list). Include known unresolved task references and discover parents from the confined inventory for workspace activity even when not selected.
3. For unresolved child references, read/verify session parentage and location; use `session.active` as present-tense execution evidence and child history/execution records as corroboration. A parent being idle is never evidence that its detached child finished. For shell references use confined `shell.get/list` and metadata ownership; do not infer background membership from every running shell in the directory.
4. Apply correlated synthetic terminal records as authoritative worker results. A child terminal execution event can trigger prompt reconciliation, but absence from active is **not** a completed/error/cancelled result. A notification may be pending in the parent inbox, not yet in history. Do not substitute an older child answer for a missing current report.
5. Merge the reconciliation result with later live updates under a generation fence; terminal evidence beats older launch/progress, and newer occurrences never inherit an earlier terminal state. Publish changes through existing ordered Uatu replay/snapshot seams. On failed reads retain last evidence and set optional `stateUncertain:true` on the task; render “Status unavailable — reconnecting” instead of asserting current running or finished. Clear it only after a successful authoritative reconciliation.

Perform this on initial inventory/attach, Uatu replay reset, provider reconnect, and relevant child/notification events of an already initialized adapter. Preserve `ChatService.activity()`'s no-start rule: dashboard/activity reads alone must not start OpenCode. Coalesce one read per parent, limit concurrency (initially four), reuse the provider's bounded history cache, and back off transient failures; avoid whole-inventory rescans per text delta or open-child polling as the source of truth. Hidden browser pages rely on the existing hub stream resume contract. Existing complete terminal history remains readable after a workspace restart; unresolved work is revalidated, not automatically declared stopped or durable.

Alternative rejected: rely on SSE replay or parent turn completion. V2 provides neither historical event replay nor that lifecycle equivalence.

### D4. Background-all is an explicit, receipt-keyed action

Introduce positive capability `background-blocking-work` only on the V2 adapter with the native method; declare existing `background-tasks` once lifecycle, inspection, recovery, and stopping are implemented. Add optional provider `backgroundBlockingWork(parentId)` calling the installed client's `session.background({sessionID:parentId})`. Thread a normalized `POST /api/chat/conversations/:id/background {requestId}` through client, agent-qualified service dispatch, adapter admission/receipt lane, and routes. Return `{accepted:true}`: 204 confirms the request, not a count or proof of continuing work. Empty eligibility is a successful no-op.

The action is labelled **Continue while workers run**, styled like other chat buttons and shown only when the capability, active parent and running blocking tool/command or confirmed foreground-task evidence coexist. Pending tools, merely generating parents, and known detached/settled/uncertain worker launchers do not qualify. A tooltip and collapsed `What continues?` disclosure explain: “Moves all eligible blocking jobs in this conversation to the background, including shell commands. It does not stop them.” Disable during its request or parent cancellation. The API exposes no exact eligibility query: this visible evidence is not a guarantee of eligible job count, so a race to no blockers remains an accepted no-op. Duplicate clicks/retries must not dispatch again **while their receipt is retained**. Transport-ambiguous failures show “Outcome unknown; refreshing” and reconcile, not an automatic new mutation. Feedback clears once the parent and workers settle with no request in flight.

For background-all and V2 worker-stop operations, catch a transport-ambiguous failure **inside** the receipt operation and resolve it with an internal tagged unknown outcome; do not let it reject through `IdempotencyReceipts.run`, which would delete the receipt. Translate that cached outcome into a stable normalized `operation_outcome_unknown` error/409 outside the receipt operation, never `{accepted:true}` or `{stopped:true}`. Keep the same unknown outcome on retries while retained, even if subsequent read-only recovery changes visible worker state. Definitive pre-dispatch validation/provider rejection can retain existing error handling when non-application is established; ambiguity after dispatch must be preserved conservatively. No change to unrelated operations' retry policy is required.

Use the existing bounded memory budget (default 1,000 entries / 512 KiB; settled receipts retained up to 15 minutes, possibly evicted earlier). No persistent store or restart recovery of receipts is added. After expiry, capacity eviction, adapter recreation, or process restart, an old request ID is indistinguishable from a new request and can dispatch again: neither the client nor documentation may promise at-most-once across that boundary. The UI must not automatically replay an uncertain mutation across reconnect/reload; re-read state and require a fresh explicit action if the user still wants it. Tests must distinguish browser-response loss after Uatu has a result from **upstream-response loss after OpenCode applied the action but before Uatu received confirmation**, then exercise TTL, capacity eviction, and a fresh adapter.

It never calls interrupt, prompt, inbox update/cancel, or child mutations. A background event may release OpenCode's blocker and let the parent continue; let provider events describe this. Do not optimistically mark every tool backgrounded on HTTP success. Preserve the draft, attachments, staged selection, queue order, and delivery preference.

Alternative rejected: background on Send, or a per-child “background” button backed by a parent-wide endpoint. Both imply effects the user did not request.

### D5. Shell consequences are part of the all-jobs contract

The approved all-eligible operation includes native shell jobs, so they cannot become invisible side effects. Normalize native background shell launch and metadata-authenticated shell completions into the same task model, keyed by shell/job occurrence and linked to their launcher. Use existing task inspection/output and stop routes with `shell.output` and `shell.remove` after checking workspace and owning parent metadata; never read a browser-supplied output path. Keep output already received inspectable within its existing retained view/history lifetime; output truncation and subsequent removal are distinct unavailable-output reasons. Do not add a persistent output archive or promise recovery of missing upstream bytes.

Shell Stop is implemented by **removal**, not a native job-cancel endpoint. An in-app confirmation explains before activation that stopping removes the provider shell record/output and may be reported as failed rather than cancelled. Cancel has initial focus; Escape cancels only the confirmation and restores the invoking control without closing its child/output view. Revalidate the selected task after confirmation. A 204 means removal was accepted (or already absent), not that a cancelled notification or final capture exists. Removal while waiting/capturing can fail the waiter or capture read; the plugin's missing-capture error yields an `error` notification. Show truthful failed outcome plus stop-request/output-unavailable context, not fabricated stopped state. A `shell.deleted` event or output 404 alone is not a job terminal result.

Completion and removal race at both the exit wait and output capture. If the plugin already captured and settled the completed result, retain that confirmed completion/report even when removal makes later output reads unavailable. If exit happened but capture was removed before the plugin finished, it can still fail: process exit alone must not force completed. Model both orderings, removal-before-exit, and already-missing 204 in source-faithful tests. The fake must delete shell record/output, fail pending waiters, and let missing capture generate error instead of hardcoding every removal as cancelled with retained output.

Do not alter ordinary foreground shell rendering or reinterpret every `source:"shell"` note as a background task: foreground user-shell transcript notes are currently suppressed because a command row already renders them. Require known background launch or equivalent correlated evidence. Keep completion state and exit/signal/timeout facts consistent. Unexpected plugin-specific jobs may also be affected by the upstream operation; show the provider's safe summary but never invent their stop/inspection contract or add plugin RPC dependencies.

Alternative rejected: silently narrow `session.background` to subagents; its public method has no type selector.

### D6. Stop targets execution, and acknowledgement is not settlement

- Parent Stop uses existing abort with `interrupt(parent, {resume:false})`, serializes against background-all, and retains steering's dormant Uatu queue / paused user steers. Label its accessible action **Stop parent** when workers exist, with explanation that still-blocking foreground work can stop but detached workers continue. Touch activation with worker records opens an in-app scope confirmation mentioning later provider wakeup; Cancel sends no request, and confirmation rechecks the same live parent. Desktop activation is unchanged. With only background workers and no parent turn, the parent Stop stays disabled.
- Worker Stop reuses receipt-keyed `stopTask(parent, taskId)`. Resolve the task server-side to its current verified child occurrence and call `session.interrupt({sessionID:child, resume:false})`; shells use D5. Never accept an arbitrary browser child ID as the mutation target. Recheck that the occurrence is still current and refuse a known superseded stop rather than redirecting it to a later continuation. Uncertain, foreign, removed, or settled targets produce the existing unavailable/conflict path without interruption. Native interrupt is session-scoped with no compare-generation precondition: this recheck cannot guarantee atomicity against a simultaneous continuation from an external client; do not claim that stronger guarantee.
- An accepted interrupt is “Stopping…” until authoritative events/history settle it. A confirmed completed result is not replaced with an optimistic stopped row; shell exit/removal/capture ordering follows D5, not a universal completion-before-stop rule. Apply D4's retained-unknown receipt handling and bounded deduplication lifetime to child/shell stop too. A network failure leaves evidence intact with actionable uncertainty; no automatic mutation retry follows. Sibling detached workers and the parent's own execution are untouched by child Stop. Native cancellation of that child's foreground descendants remains native execution semantics, not a new “stop all workers” feature.
- Native completion, including cancelled/error notices, can resume the parent after a parent stop. State this in the UI/help; a parent stop is not a persistent ban on future provider wakeups. Uatu sends no synthetic notification or resume call and does not delete pending inbox input.

Alternative rejected: stop every child from parent Stop, or synthesize cancellation on an interrupt response. Neither matches the provider contract.

### D7. Shared frontend, activity, and notification behavior

Use `runningBackgroundTasks`, `subagentEntries`, `TaskInspectionPanel`, existing task list and child drill-down, not a second worker dashboard. Pass settled task facts into the child strip so it remains attached after completion; result links and child transcripts remain available from historical launch/result rows. Deduplicate worker counts across launcher and task references. Child history is fetched by exact provider-qualified ID even when excluded from the top-level picker; list membership is not authorization. Failed opens retain the parent/draft and expose Retry instead of a dead control or fallback to the wrong session (#522 regression).

One canonical worker state drives the card, track, task list, open-child strip, composer summary, and existing workspace activity. Mixed foreground/background keeps parent working status while still listing workers; an idle parent with live tasks uses `background` and accepts a new prompt normally. Child permission/question requests continue through existing mirrored request and needs-answer paths. A reconciliation failure does not announce finished: retain last-known activity conservatively and show uncertainty in chat until evidence returns.

Use existing normalized settled task rows as the in-app completion notification; one report body, outcome in words, links back to launch and child. Present a correlated result after its launcher even if the worker's retained start timestamp is earlier. There is no new toast/push delivery subsystem. Preserve `web-push-notifications`: child completion, hydration, replay, and entering background do not produce top-level success push. An actual subsequent parent turn completing still follows the existing policy.

Preserve steering's separate Send, delivery selector, and Stop; Continue is a distinct task-area action, never a send mode. Use rem/token styles with at least 2.75rem targets and 0.5rem horizontal and vertical action gaps, visible focus and outcome text, polite non-duplicated announcements, and reduced motion. V2 reserves the parent Stop footprint before worker appearance. Touch keeps the secondary subagent track collapsed by default for already-listed background workers. Worker controls remain inspectable through the shared scrollable dock during hardware-keyboard composition outside short landscape. Software-keyboard mode or short landscape hides non-queue tracks and Continue; dismissing the keyboard or leaving short landscape restores them. Pending counts, batch Send and replacement warnings remain available. Preserve touch composer focus through activation so blur-induced layout changes cannot swallow a visible worker/summary tap. Child opening moves focus into the drill-down; Back/Escape restores the invoker without losing the draft or dismissing multiple layers. Test settlement while child/output views are open.

The steering dock shares height, not scrolling: Workers and Pending are matching sibling cards whose headers remain outside independent contained content panes. The explicit independent-pane request supersedes the earlier shared-scroller contract; compact-chat-background-steering documents redistribution and physically insufficient bands. Normal touch budgets remain 35% of visual height, 25% from 48rem width, or 24% during hardware editing. The parent composer stays compact at software-keyboard heights at most 450px and landscape bands at most 390px high and at least 600px wide; existing request-answer behavior and safe insets remain unchanged. Expanded tracks hide the prompt rail to protect action hit regions. Dock growth reserves final layout height before its 160ms clip reveal; reduced motion skips the reveal. Desktop uses measured panel height, not a rem or window-height fallback; see steering D10.

Alternative rejected: child sessions in the top-level picker or an embedded child composer. Inspection already has a seam and direct child messaging is not approved.

The subagent disclosure tracks automatic versus deliberate expansion: when foreground work detaches, only its automatic duplicate expansion collapses. Shell confirmation captures the actual invoker (including WebKit pointer activation); if settlement removes it, restoration prefers the surviving action in the same task inspection, then its Back/timeline control, before the composer.

The disclosure retains both the DOM open state and its automatic/deliberate provenance across conversation selection. Only conversation-specific running/collapse bookkeeping resets; selecting another conversation does not turn a retained automatic expansion into user intent.

Treat the current `opencode-v2-steering` implementation/planning as the integration baseline; do not edit its artifacts to claim it covers #457. This delta adds requirements instead of replacing its prompt/queue requirements. Extend synthetic-source handling adjacent to, not inside, user-steer ownership: worker notices never become editable queued user messages, and delivered user rows still obey steering's boundary rule. Background-all and parent Stop use the existing admission lane; worker Stop uses a task-target receipt lane plus authoritative occurrence validation, without holding a parent-wide lock until the worker finishes.

The existing generic `listBackgroundTasks` behavior stays for providers that support its assumptions; V2 uses D3's evidence-bearing reconciliation. Teach snapshot/status reconciliation not to close detached workers when a parent turn ends or a projection is evicted. Keep deliveryPaused/dormant queue decisions independent of the presence of live workers: backgrounding itself neither flushes nor pauses the held queue; ordinary parent lifecycle still does what steering specifies.

Publish the capability and optional `stateUncertain` field in `types.ts`, strict validation and OpenAPI schemas, and classify the new route consistently with existing internal session-child mutations. Update the API revision/changelog from the **actual implementation baseline** (steering already plans revision 25); allocate the next coordinated revision, not another hardcoded 25. ## Risks / Trade-offs

- [No public generic job list or occurrence ID] → Reconstruct confined parent/child facts, preserve readable unmatched results, and expose uncertainty instead of miscorrelating repeated-child work. Do not rely on a made-up job endpoint.
- [Cross-read snapshots race with live updates] → Connected-before-read plus generation fence, monotonic per-occurrence merges, and fixtures where terminal evidence arrives during reconciliation.
- [Cold workspace inventory recovery is expensive] → Reuse complete-history caching, coalesce/bound reads, and reconcile only candidate parents; test request counts and that text deltas do not fan out reads.
- [Parent interruption and child cancellation are asynchronous; native interrupt has no occurrence precondition] → Distinct controls, pending state, receipt deduplication, terminal confirmation, and completion-wins race assertions. Refuse known superseded targets; document the residual check-to-interrupt race with external continuations rather than promising an unsupported atomic generation lock.
- [Transport failure after provider application would delete an ordinary rejected receipt] → Cache tagged unknown outcomes before translating errors; test both response-loss boundaries. Deduplication remains bounded by TTL/capacity and adapter lifetime, with no durable at-most-once claim or automatic replay after uncertainty.
- [Shell removal destroys record/output and may cause job error even after process exit] → Explain destructive semantics; preserve known content only for its existing retention lifetime, show failed/output-unavailable truthfully, and test exit/capture/removal orderings against pinned source. Do not normalize every stop request to cancelled.
- [Background-all also affects plugin-defined jobs] → Explain all-eligible semantics and retain safe provider summaries, but expose no fictitious per-job controls.
- [Service restart behavior differs between server versions and worker kinds] → Recover observable history/state only; source inspection of recovery internals is not an uptime guarantee. No service restart is performed for planning.
- [New UI could regress the uncommitted steering UX] → Add task-area action without replacing the composer rail, retain all existing steering/accessibility tests, and review final diffs for accidental unrelated changes.

## Migration Plan

Implement only after planning approval, on top of the retained steering work. No database migration or new persistent Uatu job store. Ship types, validators, route, provider, UI assets and API revision together; old/new client mismatch follows the existing freshness handshake. Completed history reconstructs on first read. Rollback removes the new capability/action and restores prior presentation without mutating OpenCode records, cancelling workers, or rewriting instructions. Do not release with skipped critical race/recovery tests; document any unavailable real-service/browser verification.
