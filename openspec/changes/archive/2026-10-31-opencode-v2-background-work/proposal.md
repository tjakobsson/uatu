## Why

OpenCode V2 completes a background subagent's launcher before its child finishes, so Uatu currently reports unfinished work as finished and renders the later completion envelope as a raw notice ([#457](https://github.com/tjakobsson/uatu/issues/457)). Users need trustworthy background state, inspection, results, and explicit controls while continuing the parent conversation, without changing agent selection or execution policy.

## What Changes

- Support the chosen OpenCode agent's native `subagent` tool with `background: true`, including work launched outside Uatu. Keep foreground execution as the provider's default; do not add project instructions, prompts, policies, or configuration to encourage background execution.
- Track worker running/completed/failed/stopped state independently of launcher completion, using the existing background-task model and subagent transcript surfaces. Preserve native `error`/`cancelled` meaning as Uatu's `failed`/`stopped` labels. Keep child results inspectable after settlement and across navigation.
- Correlate provider-owned synthetic completion notifications with their worker and launcher; show a readable settled task/result instead of raw envelopes or launch instructions masquerading as results. Never inject a second notification or wake the parent ourselves.
- Reconcile background work from provider history, pending synthetic inbox items, and current execution on attach and provider reconnect. Missing evidence remains visibly uncertain, not fabricated success or cancellation. This is not a promise that jobs survive a service restart.
- Add explicit **Continue while workers run**, which calls `session.background` once for the parent and backgrounds **all eligible blocking jobs**, including shell jobs. It does not cancel, submit a draft, or send steers. Shell work affected by this operation remains visible and inspectable through existing task/output seams; no separate job-management product is introduced.
- The UX audit limits visible Continue to running blocker evidence, excludes pending/detached/uncertain launcher facts, collapses its explanation, clears settled feedback, and uses consistent rem/token controls. Touch avoids automatically expanding duplicate worker presentations and budgets all tracks together. Hardware-keyboard composition keeps worker controls in the scrollable dock; software-keyboard/short-landscape layouts hide them until that compact state ends, while retaining pending safety information. Touch parent Stop explains its scope in-app before confirmation. Shell removal retains its destructive confirmation with layered Escape and focus restoration.
- Distinguish **Stop parent** from **Stop worker**: parent interruption can cancel still-blocking foreground work, but does not stop detached workers; a worker stop targets only the verified child (or associated shell). Provider completion may subsequently wake the parent. Preserve steering's dormant held queue and paused pending-steer behavior.
- Treat native shell removal truthfully: it removes the provider record/output and can produce a failed job notification rather than cancellation. Preserve already available output within its retained view/history lifetime, disclose output loss, and do not promise a stopped outcome or recoverable output after removal.
- Count live background work in workspace activity while keeping the parent composer usable. Add desktop, keyboard, touch, reconnect, mixed foreground/background, and cancellation-race coverage.
- Extend normalized contracts only where needed: positive capability for backgrounding blocking work, a receipt-keyed parent mutation, and explicit uncertainty on recovered task state. Preserve transport-ambiguous background/worker-stop outcomes in bounded in-memory receipts instead of dropping them as retryable errors. Deduplication lasts only while the receipt is retained (default up to 15 minutes after settlement, subject to capacity eviction) and never across adapter/process restart; no persistent receipt store is added. Update strict validators and the workspace API revision together at implementation time; do not upgrade the installed client merely for this feature.

## Capabilities

### New Capabilities

None; this extends the existing OpenCode conversation contract and reuses shared task presentation.

### Modified Capabilities

- `opencode-chat`: Native V2 background lifecycle, correlated completion/result presentation, scoped child inspection and stopping, reconnect recovery, explicit background-all action, workspace activity, and accessible controls. Existing shared capability gating, stream confinement, and web-push exclusion of child completions remain in force.

## Impact

- Primary issue: [#457](https://github.com/tjakobsson/uatu/issues/457). [#522](https://github.com/tjakobsson/uatu/issues/522) supplies navigation regression context; this change must reliably open its own background children but does not claim to diagnose or close every cross-provider navigation defect.
- Integration baseline: `opencode-v2-steering` explicitly excludes #457. Implement this change on top of its current provider/adapter/UX seams, without rewriting its scope or replacing Send/Stop/delivery controls. Synthetic worker notifications stay out of its user-only steer dock. Coordinate the API revision with that change instead of hardcoding a second revision 25.
- Implementation areas: `src/chat/opencode/v2/{normalization,provider}.ts`, existing shared normalization, `provider.ts`, `adapter.ts`, projection/task reconciliation, `types.ts`, `validation.ts`, service/registry/client/routes, `timeline-renderer.ts`, `background-tasks.ts`, `task-inspection.ts`, `ui.ts`, and related UI styles/markup. Reuse existing task-stop, child-history, multiplexed stream, interaction mirroring, notification, and activity paths.
- Verification: colocated normalization/provider/adapter/rendering tests, contract tests, and the existing real-provider scripted V2 E2E harness. Pin fixtures to inspected OpenCode **2.0.29** behavior with the installed `@opencode/client` **2.0.28** contract. A later explicitly authorized isolated real-provider check is a separate implementation acceptance gate, not part of this planning run.
- Documentation/contracts: `ARCHITECTURE.md`, SDK coverage annotations, `api/openapi.yaml`, route coverage/exclusions, API changelog/version and affected user-facing behavior documentation in the eventual implementation. No dependency installation or upgrades, product edits, live-session mutations, commits, or publication in this planning change.
- Excluded: automatic background-on-send, direct child messaging, installing or editing project instructions, new agent/model defaults, new OS/web-push worker alerts, broad #522 remediation, and unconditional restart durability guarantees. An optional user-facing documentation tip is permitted: prefer background subagents for independent work when useful non-overlapping work can continue; keep dependent work foreground, avoid overlapping writes or use isolation, and do not poll for completion. This is advice only, not a policy/configuration change or an instruction to always background work.
