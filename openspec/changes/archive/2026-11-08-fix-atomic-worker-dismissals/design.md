## Context

See proposal.md for reproduced failures. `worker-dismissals-api.ts` currently fetches up to twenty 100-message display-history pages, each capped at four MiB. `ui.ts` awaits one client POST per eligible worker. Store reconciliation can commit new evidence before committing the requested singleton dismissal. `WorkerDismissalsStore` additionally orders trusted observations, admitted target authority, the store queue and the workspace lifecycle queue; these safeguards must remain effective for every batch target.

The chat adapter already receives provider `completeItems` and currentness guards. OpenCode V2 reads complete history internally and pages it locally. Its covered-history owner protects generation, source changes and parent/child association evidence. Reusing that owner is preferable to inventing a new unguarded provider read or trusting a previously cached UI projection.

## Goals / Non-Goals

**Goals:** one explicit group, one authoritative read outcome, one successful durable save, one visible dismissal outcome; bounded evidence transport independent of transcript text size; complete source and concurrent activity protection.

**Non-Goals:** eliminating the provider's own complete-history read/normalization, changing task lifecycle or Stop authority, raising runtime timeouts, modifying authentication/storage safety, diagnosing the live reconnect, implementing #581, or claiming every #592 failure resolved.

## Decisions

### Compact evidence at the owned history seam

Add a worker-only complete read mode behind the chat adapter/service. Consume `completeItems` from one provider read when available, under the existing history currentness/recovery owner. Select only worker/launcher rows for downstream attribution/projection and reuse the existing dismissal identity/evidence projection after full launcher reconciliation. Providers without complete source support use a bounded row-only fallback with advancing cursors and retained page currentness guards; exhaustion fails closed. The fallback refuses any provenance-bearing page (including association contradictions, origins, hidden results, fallback/revert metadata, accounting or opaque source ownership) rather than dropping facts or treating them as independently unionable decorations. All three production providers supply `completeItems`; their complete-source path retains its existing provenance reconciliation. The existing source/evidence capacity remains 8192, with explicit refusal before returning an over-capacity set.

Expose this through a compact internal child resource and agent-qualified dispatch. Share server-side evidence projection between that resource and trusted Hub observation rather than diverging identity rules. Return a closed versioned envelope identifying the conversation, explicit complete coverage and bounded evidence facts. Validate every field in the Hub. Do not retain transcript text in the envelope or reuse browser-supplied claims.

Validate each current worker/launcher source before presentation liveness normalization or any row-id deduplication. A repeated row id must agree on occurrence namespace, lifecycle, association and launcher facts; visible page rows must agree with complete coverage. DTO type collisions and malformed rows refuse the read. Compatible duplicates may differ in display text, background display clocks, observation clocks, alias ordering or primary choice within the same proven alias set. After validation, coalesce those compatible duplicates so a later owned recovery update cannot leave a stale duplicate shadowing it. Validate recovery arrays before their own id index and validate retained rows before the final source-reconciliation map. Legacy live inventory is checked before its first-row-wins membership handling. Independently owned recovery/live sources are validated separately rather than mistaken for duplicate rows in one snapshot; they still cannot weaken current source protection without a fresh coherent source view.

Cross-row validation also checks shared exact execution aliases, including unsettled rows that do not themselves produce dismissible evidence. Shared-alias groups accumulate immutable task, child, task-type, foreground, launcher, result and launch-reference facts. Unknown optional facts never overwrite known facts, and joining alias groups must reconcile every prior group's facts rather than keeping a last-row signature. Strong known launcher sets must agree; the existing legacy terminal call/result alias enrichment remains permitted when task/child facts are compatible. Cohort knowledge cannot resurrect a bare task anchor established to be only a child id. Preserve established launcher suppression and strong provider alias namespaces; a shared child session alone is not an alias. This seam can validate normalized provider source arrays, not facts already discarded inside a provider; existing provider coverage/currentness guards remain required.

For compact reads, current source rows precede retained projection rows. Empty or failed recovery can withdraw old cache observations but cannot unverify a current source row. Weak launcher/result supersession refuses before deleting a current protected row. The late retained-terminal override requires a change during the covered read, not a pre-existing cached terminal row. A final prepublication source-strength assertion protects all merge paths: activity, nondismissibility, exact identity, immutable associations and generation cannot silently weaken. A mixed view that would grant dismissal fails unavailable; a fresh complete source read must establish a settled/weaker state. This assertion does not treat cache-write order or clocks as independent newer lifecycle authority. Ordinary chat-history/event-pump behavior is unchanged.

Native canonical alias enrichment is a narrowly certified exception to cross-row task/launcher equality, not to same-row or supplemental coverage validation. OpenCode's native launcher key is call-scoped (`v2:<parent>:<call>`), while complete child execution history may prove several calls share one occurrence and retain the first key with all launch aliases. An old running/unavailable row with no result, request or end fact can be discarded only when both rows independently permit dismissal, share parent/child agent scope, use their exact native call-scoped row/task recipes, and a strictly larger canonical launcher set fully contains the member launcher set. Each row must have one native execution alias per launcher, and canonical aliases must fully contain member aliases. Known member generation/launch-reference facts must agree with the canonical row; conflicting known subagent types refuse. Positive/checking/session-active rows and conflicting terminal outcomes are never shadows. Validate the remaining alias cohorts strictly, so discarded abstentions cannot bridge incompatible canonical rows. This projection does not change lifecycle attribution, native Stop proof or provider coverage requirements.

Alternative rejected: increase the existing twenty-page or four-MiB display-history limits. It preserves repeated expensive reads and ties presentation-only dismissal to arbitrary transcript output volume. An unguarded cached-projection read is also rejected because missing historical rows or stale activity cannot authorize durable hiding.

### Atomic batch within existing store ownership

Keep singleton dismiss/retire compatibility; add a closed explicit bulk-dismiss shape. Bound targets by the existing 8192 identity budget and body bytes by the existing four-MiB state envelope, retaining the existing four-KiB limit for singleton requests. This is a new bounded batch contract, not a larger allowance for transcript transport. Reject empty, duplicate and malformed targets before admission.

Admit every exact target before entering the workspace lifecycle lane, with independently captured revisions and activity authority. Release every request admission on abort/failure. A batch atomic write retains an independent observation reference through publication or I/O failure: abort may occur before a first staged record exists, and must not withdraw observation ownership from the already-running disk operation. On publication that owner schedules any captured positive activity for durable retirement even if the requesting client has departed. It is bounded by the existing target budget, does not authorize new mutations, and is released when the sole disk operation drains. Reconcile evidence once into a staged map, validate every requested target against current revisions and admission-time activity fences, apply every selected dismissal to that map, and commit once before memory publication or invalidation. On conditional refusal, trusted positive-activity retirement remains durable but no requested dismissals are applied. Preserve atomic temporary-file persistence and all file safety checks.

Alternative rejected: parallel singleton requests. They still repeat evidence reads and disk commits and allow partial successful groups. Blind optimistic UI removal is rejected as an answer to performance because it cannot establish durable success.

Conditional validation reads retained fences without allocating new ones for staged records. First-record activity stays owned by admission/commit references until publication; only retained records acquire durable visibility fences. Repeated byte-capacity or persistence failures therefore cannot grow unpublished fence ownership beyond the record budget.

### One client action and visibility result

Add a batch client method using the same selection epoch, positive-observation visibility fences and per-execution failure ownership as singleton actions. The UI captures currently eligible proven identities, deduplicates them and sends one request. Unsupported identities retain skipped feedback. Active/unresolved workers stay visible. Apply the successful state once; on failure retain rows and explicit uncertainty. Account invalidation remains one category notice, not a mark payload. Preserve one coalesced refresh after queued invalidations: the current protocol cannot distinguish self-notices from a later update on another device, so silently discarding those notices would weaken recovery. Counters for the explicit bulk operation exclude that subsequent independent reconciliation.

Singleton operations retain their established first-record admission save and activity ordering for compatibility; the new bulk path stages evidence and selected changes together. Conditional validation is the batch linearization decision. As with existing singleton writes, positive activity arriving during persistence remains captured by admission authority and retires affected marks on release; client observation fences keep those workers visible while that retirement completes.

### Contract and release alignment

Update `api/openapi.yaml`, relevant capability deltas and architecture prose together. The internal child route stays in the existing workspace route-family exclusion rather than becoming a public OpenAPI operation. Existing stored version-1 records remain unchanged. Defer #581's separate diagnostic sink and comprehensive redaction matrix. No changelog edit: a dismissal-only fix requires the poststable-feature chore override documented in CONTRIBUTING.md. The combined PR with `fix-live-burst-recovery` must instead retain a visible fix for its independently reproduced stable reconnect defect; describe dismissal stabilization separately.

## Risks / Trade-offs

- [Provider normalization remains expensive] → one complete-source operation per batch; deterministic counters distinguish removed amplification from remaining source cost.
- [Coverage refactor accidentally loses generation/association fences] → exercise real adapter/provider paths with concurrent activity and source changes, not only mocked compact HTTP responses.
- [One stale target refuses the group] → explicit atomic contract; preserve rows and require a fresh user decision rather than automatic retries.
- [Large batches retain many admissions] → use existing bounded identity/admission capacity; reject overload and release all authority after every outcome.
- [Old workspace child lacks compact resource] → fail visibly; no silent fallback to the old transcript transport or partial evidence. Upgrade/restart the child with the Hub build.

## Migration Plan

No persisted data migration or safety-setting changes. Deliver client, Hub and child contracts together. Validate singleton compatibility, bulk behavior, source coverage and failed persistence before independent review. Rollback reuses the unchanged version-1 store; in-flight actions remain unconfirmed until explicitly refreshed.
