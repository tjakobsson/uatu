## Context

`scripts/agent-coverage.ts` has three layers:

1. **Extraction** reads the vocabulary from the installed SDKs' declaration files and fails loudly when an axis comes back empty.
2. **Probing and annotation** classifies each entry by running uatu's normalizers and `describeToolDetail` on a stub of it. It applies the hand-written annotations in `src/chat/*/sdk-coverage.ts` and rejects stale or unexplained ones.
3. **Output** renders a matrix per agent, an SVG badge per agent (`badge-maker`) and a README block. It also keeps a sealed "Since …" section, comparing against the matrix committed at `HEAD` (`committedBaseline`). `staleOutputs()` compares all of this with the files in the repository.

Layers 1 and 2 are what catch real breakage. Layer 3 is what makes every bump red. Today the only thing that runs layers 1 and 2 against the installed SDKs in CI is the freshness test, through `generate()`. Deleting that test without a replacement would also stop CI from catching stale annotations.

The rendered matrices are about 9 KB (Claude Code) and 18 KB (OpenCode, covering both generations), 28 KB together. GitHub caps an issue body at 65,536 characters.

## Goals / Non-Goals

**Goals:**
- An agent SDK PR from Renovate passes CI unless uatu's code or annotations must change.
- The dashboard is generated by the same probing code as today. Only where the output goes changes.
- The logic that decides the dashboard body and the comment is pure and unit-tested. The workflow only does I/O.

**Non-Goals:**
- Renovate automerge configuration (a separate change).
- Changing how entries are classified, what the five states mean, or the annotation format.
- Keeping the old "Since …" history. Git history keeps it.

## Decisions

### One issue, identified by number in the repository

The dashboard is one issue, created once by hand during apply. Its number is a constant in `scripts/agent-coverage.ts`, and the README links to it. The workflow edits that issue and fails if it does not exist. It never creates one.

*Alternatives:* looking the issue up by label or title and creating it when missing would survive someone deleting the issue, but could also produce a second dashboard and leave the README link pointing at the old one. One issue per agent would give each its own size headroom and comment thread, but would need two links and two places to check. One issue holds today's report with more than half the limit to spare. If it ever outgrows that, the size check fails loudly and splitting per agent becomes the fix.

### The generator renders; the workflow publishes

`bun run coverage:agents` keeps its name and becomes a pure renderer. It accepts an optional `--previous <file>` (the current issue body) and writes the new body, plus the comment when there is one. With no arguments it prints the body to stdout as a local preview. The workflow fetches the body with `gh issue view`, runs the generator, posts the comment with `gh issue comment` if one was produced, and then edits the body with `gh issue edit`, but only if the body changed.

*Alternative:* calling `gh` from inside the script. That puts the token and network failure handling in TypeScript that unit tests cannot exercise. Keeping the script pure means tests cover everything that decides what is published.

### The published vocabulary lives in a hidden marker in the issue body

The body ends with `<!-- agent-coverage:state v1 {...} -->`. It holds JSON with, for each agent, the version line and the sorted entry names per axis id. In the JSON, the second hyphen of every `--` is written as the escape `-\u002d`, so no entry name can close the comment early. The next run parses the marker to compute what was added and removed. If the marker is missing, its version is unknown, or it fails to parse, there is no baseline: publish and post no comment.

*Alternatives:* parsing the vocabulary back out of the rendered tables, as `parseMatrix` does today. That ties the diff to table formatting, and a later formatting change would read as "everything removed". The SHA-256 seal on the old "Since …" section guarded against hand edits to a committed file, which an issue does not need: GitHub records every edit in the issue's history. The seal is dropped.

### Comment first, then edit the body

The body is the baseline for the next diff, so it is updated only after the comment is posted. If the run fails between the two steps, the next run finds the old baseline and posts the comment again. A duplicate comment is the accepted cost; a lost comment is not. Bumps that land while no run completes accumulate against the last baseline and appear in one comment, which is what the spec's "Bumps between publications are reported together" asks for.

### Deterministic body, no run metadata

The body contains no timestamp, commit SHA or run link. That makes it a function of the SDKs and the code only. The workflow can then skip the edit when nothing changed, and the issue history only records real coverage changes.

### Workflow shape

`.github/workflows/agent-coverage.yml` runs on `push` to `main` and on `workflow_dispatch`, with no path filter. Coverage depends on `package.json`, `bun.lock` and code anywhere the normalizers import from. A path filter would risk missing a change, and a run costs about half a minute. The job is guarded by `if: github.repository == 'tjakobsson/uatu'` and has `permissions: { contents: read, issues: write }`. It checks out with `persist-credentials: false` and uses the same SHA-pinned `actions/checkout` and `oven-sh/setup-bun`, and the same Bun version, as `ci.yml`. It uses `concurrency: { group: agent-coverage, cancel-in-progress: false }`, so a run that has posted a comment always gets to update the body.

### What stays in the unit suite

The extraction, classification and annotation tests stay. The freshness tests are replaced by one test that builds both agents' reports from the installed SDKs: controls, extraction, probes and annotations, the same path publication takes. A stale annotation or an extraction failure therefore still fails CI on the Renovate PR itself. The old output tests (committed baseline, "since" seal, badge colour, README block) are replaced by renderer tests:
- determinism
- marker round-trip, including a name containing `--`
- diff content and the versions in it
- no comment on a version-only change
- no comment when the marker is missing or garbled
- the size guard

### Removed

`docs/agents/` and the generated README block are removed, and so is `badge-maker` (only `renderBadge` uses it).

## Risks / Trade-offs

- [The dashboard only updates after merge, so a PR author doesn't see their effect on coverage in the PR] → `bun run coverage:agents` previews the body locally, and `--previous` with the current issue body previews the comment. CONTRIBUTING says how.
- [Someone edits the issue body by hand and breaks the marker] → The next run treats it as having no baseline: it republishes and skips one comment. That loses at most one diff, and GitHub's edit history shows what happened.
- [The report grows past the 65,536-character limit] → Publication fails, naming the size, and the old dashboard stays. Splitting into one issue per agent is the planned fix.
- [The issue is deleted or transferred] → The workflow fails, naming the issue number. Fix: create a new issue and update the constant and the README link.
- [Gaps are no longer visible in a checkout or offline] → Accepted in the proposal. The dashboard is a maintainer tool.
- [The workflow token's rate limit or a GitHub outage] → The run fails visibly. The next push or a manual dispatch catches up, because the diff is computed against the last published state.

## Migration Plan

1. Create the dashboard issue (title "Agent SDK coverage", placeholder body) and record its number.
2. Before merge, publish the baseline by running the workflow's steps by hand (`workflow_dispatch` only works once the file is on `main`). That run finds no marker and posts no comment.
3. Merge the change. The first workflow run on `main` finds the baseline and an identical body, so it neither comments nor edits.
4. Renovate rebases #470, #472, #473 and #474. They touch only `package.json` and `bun.lock`, so they go green. Their merges then produce dashboard updates, with a comment only where vocabulary changed.

Rollback: revert the merge commit, which brings back `docs/agents/` and the freshness tests, and run `bun run coverage:agents` to bring the files up to date. Close the issue.
