## Context

See proposal.md, Why.

Today the persistent approval is a one-click reply. `renderPermission()` in `src/chat/timeline-renderer.ts` emits `Allow once` / `Allow always` / `Reject` buttons carrying `data-permission-outcome`; the click handler in `src/chat/ui.ts` (`wireItemInteractions` → `resolvePermission`) posts the outcome straight to the API. The only scope information on the card is the agent's `permissionScopeNote` sentence, which describes reach and lifetime in prose and cannot name the patterns because they are never carried.

The patterns exist upstream. OpenCode's request carries `always` (verified at commit `830d5eb5`: `packages/opencode/src/permission/index.ts` installs an allow rule per `existing.info.always` entry on an `always` reply; `tool/shell.ts` derives `<prefix> *` from the command's tokens). `src/chat/opencode/normalization.ts` reads `patterns`/`resources` under both `permission.asked` and `permission.v2.asked` and discards `always`; `listPermissions()` in `sdk-v2-provider.ts` discards it too. Under Claude Code the equivalent is the SDK's `suggestions` array on the `canUseTool` callback; `replyPermission()` in `src/chat/claude/provider.ts` already forwards `sessionScopedSuggestions(pending.suggestions)` on an `always` reply and drops the rest, so the honest list is exactly what that filter returns.

The permission item is a published wire shape (`PermissionItem` in `api/openapi.yaml`, `additionalProperties: false`), parsed on the client by `parsePermissionRequest()` in `src/chat/validation.ts`. Timeline cards are rebuilt from item state on every render; any purely client-side stage has to live in state the renderer is handed (the `expanded` set is the precedent), not in the DOM.

## Goals / Non-Goals

**Goals:**
- The persistent reply is sent only after the user has seen, in the owning agent's own syntax, exactly what it authorizes.
- The scope shown is the agent's, never derived client-side from the displayed command.
- One confirmation implementation for both agents; agent differences are confined to what each provider puts on the item and the lifetime sentence it already declares.
- The recovered form of a request confirms with the same scope as the live form.

**Non-Goals:**
- Changing what the persistent reply grants, or when it is offered. Reach and lifetime stay as they are; this change only makes them visible before the fact.
- Editing the patterns before confirming (OpenCode's TUI does not offer this either).
- A modal dialog. The confirmation is a stage of the card, in place.
- Persisting the confirming stage across reloads or between clients.

## Decisions

**D1. One additive wire field: `PermissionItem.alwaysPatterns?: string[]`.** Strings in the owning agent's own syntax: OpenCode's permission patterns (`git status *`), Claude Code's rule strings (`Bash(git status:*)`). The client renders them verbatim, so it needs no agent-specific knowledge. Optional on the wire: the field is present on every pending item the providers produce (an empty array when the agent supplied nothing reusable); absent only for items produced before this change or by a provider that does not speak to it. Both absent and empty render as "no reusable pattern". *Alternative:* a structured object per pattern (`{ kind, value }`) to distinguish rules from directories from mode switches. Rejected: the client would then need to know each agent's vocabulary to render it, and the strings the agents themselves show are already self-describing. Additive for readers, but the item schema is closed (`additionalProperties: false`), and the repository's compatibility policy treats a new property on a closed response object as breaking, so this is workspace API revision 15 with its own changelog section and migration guidance.

**D2. OpenCode: read `always` under both event-naming generations and in the pending list.** `permission.asked` (classic bridge) and `permission.v2.asked` both get `alwaysPatterns: stringArray(data.always ?? data.save)`; `listPermissions()` reads the same pair. The normalization comment records the bridge as `save`→`always`, and the existing `permission.asked` fixture already carries `always: []`, so both spellings are tolerated rather than guessed. The `permission.replied` upserts keep carrying no patterns; the projection merge retains the ask's, as it does for `resources` today. A live capture from OpenCode 1.18 against a shell permission is added as a fixture so the field name is proven, not assumed.

**D3. Claude Code: derive the list from the very filter the reply uses.** A pure `describeSessionScopedUpdates(suggestions)` in `src/chat/claude/normalization.ts` renders each update `sessionScopedSuggestions()` would forward: `addRules`/`replaceRules` with `allow` behavior as `Tool(ruleContent)` or bare `Tool`; `addDirectories` as the directory path prefixed to say it is a working-directory grant; `setMode` as the mode change. `replyPermission()` and the list share one filter so the confirmation can never diverge from the reply. Anything the filter drops (a `userSettings`/`projectSettings`/`localSettings` destination, a `deny` rule, `removeRules`) is neither forwarded nor listed, which the spec now requires. *Alternative:* forward only `addRules` and list only those. Rejected: it would silently narrow today's reply; the change is about visibility, not reach.

**D4. The confirmation is a card stage driven by a client-side `confirming` set, not a DOM marker.** `ui.ts` keeps a `Set<string>` of permission item ids in the confirming stage per timeline (the parent's and a drill-down's are distinct, like their projections), passed to `renderer.render()` next to `expanded`. `renderPermission()` renders the generic pair when the id is absent and the confirmation body when present. The set is cleared for an id on Confirm, Cancel, Escape, when the item resolves, and when the item stops being the conversation's active request. Not persisted: a reload returns to the pending prompt, which is what Cancel does too. *Alternative:* an attribute on the card like `data-auto-open`. Rejected: that pattern exists because those states are unrecoverable from item data; this one is a user choice the renderer should be told about, and reading it back from DOM the renderer is about to replace is the fragility the `expanded` comments warn against. (Implementation note: the set lives on the renderer instance rather than as a `render()` argument, since each timeline already has its own renderer, which is the per-timeline scoping wanted. The pinned outstanding-requests control turned out to be a jump pill, not a second rendering of the cards, so there is no second view to keep in step.)

**D5. Confirmation content, in order.** A title line, "Allow always?", with the action (`item.action`) beside it as a label rather than inside a sentence, because under Claude Code the action is a whole title ("Claude wants to edit hello.sh") and only a label slot reads well for both agents; the pattern list, each entry as `<code>`, visibly separated from the request's resources list, which stays above it; the agent's `permissionScopeNote` as the lifetime sentence, unchanged; then **Confirm** and **Cancel**. Two special cases mirror OpenCode's TUI: a sole `*` pattern renders no list and states that every `<action>` request will be allowed; an empty or absent list states that the agent reported no reusable pattern and confirming covers only this request. The `permissionScopeNote` also stays under the generic pair on the pending card as today, so the existing "Persistent approval states the authority it grants" scenario still holds before the user has clicked anything. *Alternative:* move the note into the confirmation only. Rejected for now: it removes a sentence users see today for a small tidiness gain; revisit with screenshots. Outcome (task 7.2): kept. On the pending card the note sits under the generic pair; in the stage it sits under the pattern list. The stage replaces the pair, so the sentence is never on screen twice, and the pending card keeps saying what Allow always reaches before anyone clicks it.

**D6. Confirm sends `approved-session`; Cancel sends nothing.** Confirm calls the existing `resolvePermission(source, id, "approved-session")`, so the wire request, receipts, and outcome label (`Allowed always`) stay unchanged, so the "Persistent approval is still sent as OpenCode's persistent reply" scenario keeps its meaning. Cancel only removes the id from the confirming set and re-renders. There is no partial state the server ever learns about.

**D7. Keyboard: Escape cancels; focus lands on Cancel.** A `keydown` listener on the timeline container (beside the existing Enter/Space file-ref handler) cancels when Escape is pressed with focus inside a confirming card, and stops propagation so the composer's own Escape handling does not fire. When the stage opens, focus moves to **Cancel**: the button that changes nothing is the safe default for a step whose purpose is to catch a slip, and Confirm is one Tab away. The `chat-request-actions` styling is reused, so touch mode needs no new controls; Escape simply has no role there.

**D8. Agent-provided choices are untouched.** A card with `choices` (a Claude plan approval) has no generic pair and therefore no confirmation stage; its intents already name what they do.

## Risks / Trade-offs

- [OpenCode's field spelling differs between event generations] → normalization reads `always` and `save`; a live-captured fixture pins the real shape; the pending-list path is tested against the same fixture.
- [The confirmation lists something the reply does not do, or vice versa (Claude)] → one filter feeds both; a unit test asserts the listed strings and the forwarded `updatedPermissions` come from the same input and agree in count.
- [An item resolves while the stage is open (answered from another tab, or auto-resolved by a broader rule OpenCode installed)] → the confirming id is dropped when the item leaves pending; the card recedes as it does today.
- [Strict API consumers reject the new field] → additive on an `additionalProperties: false` schema; changelog entry in the current unreleased section tells strict consumers to admit it. `api/contract.test.ts` and route-coverage run in CI.
- [Two extra clicks on every persistent approval] → intended; the issue asks for it and OpenCode's own client does the same. Allow once stays one click.
- [Confirm/Cancel focus placement surprises keyboard users who expect Enter to proceed] → Cancel is the harmless default; the buttons are labelled and adjacent. Revisit if screenshots or use say otherwise.

- [Claude Code's whole-tool rule is a bare tool name, not `*`] → the renderer flags only OpenCode's `*` as whole-permission; a bare `Bash` rule is listed verbatim, which is accurate but not the said-plainly warning. Follow-up: let the agent declare its wildcard spelling beside `permissionScopeNote`.
- [Escape in the stage stops propagation, so an open find bar does not close on that press] → the stop is what keeps one Escape from also closing the drill-down; a second Escape reaches the find bar. Follow-up: one chat-surface Escape dispatch over its dismissible layers.

## Migration Plan

No data or storage migration. Existing pending items without `alwaysPatterns` render the "no reusable pattern" wording until they are re-announced or recovered. Rollback is a revert; the wire field is optional and ignored by older clients.
